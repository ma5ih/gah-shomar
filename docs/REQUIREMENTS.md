# REQUIREMENTS — نیازمندی‌های محصول

Version: 1.1.0-draft
Status: IN_PROGRESS
Last updated: 2026-10-02

## نیازمندی‌های تأییدشده

- REQ-001 — محصول Mobile-first و App-like.
- REQ-002 — تقویم اصلی خورشیدی/ایرانی با نظام نمایش شاهنشاهی.
- REQ-003 — سال در UI با شماره شاهنشاهی نمایش داده شود؛ نمونه ۲۵۸۵.
- REQ-004 — نام ماه‌ها دقیقاً مطابق CALENDAR-SPEC، از جمله «اَمرداد» و «اسپند».
- REQ-005 — Today مرکز تجربه محصول باشد.
- REQ-006 — تقویم ماهانه با تعامل لمسی، navigation و جزئیات روز.
- REQ-007 — Event Entity ساختاریافته و قابل ارتباط.
- REQ-008 — داده تاریخی مهم باید منبع و وضعیت اعتبارسنجی داشته باشد.
- REQ-009 — مناسبت‌ها و داده تاریخی باید امکان بررسی و تأیید ماه‌به‌ماه داشته باشند.
- REQ-010 — صفحه مستقل Important Events.
- REQ-011 — Important Events باید ارائه بصری، تصویر باکیفیت و محتوای ساختاریافته داشته باشد؛ تصویر شاخص هر رویداد باید برای صفحه مستقل انتخاب/تهیه شود.
- REQ-012 — هر Event مهم باید صفحه جزئیات با روایت، تصاویر، افراد، دوره و منابع داشته باشد؛ مکان و نقشه در MVP الزامی نیستند.
- REQ-013 — Timeline مستقل تاریخ ایران.
- REQ-014 — Person Entity مستقل.
- REQ-015 — Personal Events شامل تولد، سالگرد و رویداد سفارشی است؛ قابلیت Reminder/Notification در MVP وجود ندارد.
- REQ-016 — Personal Person Entity.
- REQ-017 — Memories برای ثبت و یادآوری خاطرات.
- REQ-018 — Search برای Entityها و داده‌های شخصی قابل توسعه باشد.
- REQ-019 — رابط بر اساس صبح، ظهر، غروب و شب به‌صورت ظریف تغییر کند.
- REQ-020 — رابط بر اساس فصل به‌صورت ظریف تغییر کند.
- REQ-021 — فارسی و انگلیسی پشتیبانی شوند.
- REQ-022 — RTL/LTR واقعی و direction-aware.
- REQ-023 — PWA از نسخه اول به‌عنوان بخشی از هدف MVP در نظر گرفته شود.
- REQ-024 — Calendar Engine، Data/Domain، Application Logic، UI و Localization از هم جدا باشند.
- REQ-025 — محتوای تاریخی در UI hard-code نشود.
- REQ-026 — محتوای تاریخی و معاصر تا حد امکان source-backed و قابل بررسی باشد.
- REQ-027 — Swipe، Bottom Sheet، Touch Target و Motion هدفمند استفاده شوند.
- REQ-028 — محصول نباید به یک تقویم وب‌سایتی یا جدول مدرن تقلیل یابد.
- REQ-029 — Event، Person، Timeline، Memory و داده‌های مرتبط رابطه منطقی داشته باشند.
- REQ-030 — GitHub باید مرجع قابل ادامه پروژه باشد.
- REQ-031 — مخاطبان اصلی شامل ایرانیان، پادشاهی‌خواهان، ملی‌گرایان، علاقه‌مندان به شیر و خورشید، طرفداران شاهزاده رضا پهلوی و طرفداران پادشاهی و خاندان پهلوی باشند.
- REQ-032 — محصول برای افراد غیرایرانی نیز باید امکان آشنایی با فرهنگ و تاریخ ایران را فراهم کند.
- REQ-033 — کاربرد اصلی باید مانند یک تقویم آشنا و آزاد باشد و کاربر را به الگوی زمانی خاص محدود نکند.
- REQ-034 — پیچیدگی غیرضروری ممنوع؛ تفاوت محصول از هویت تقویم، محتوا و کیفیت تجربه بیاید.

## نیازمندی‌های تقویم

- REQ-035 — سال هجری شمسی معمولی نباید در UI کاربر نمایش داده شود.
- REQ-036 — میلادی فقط به‌صورت فرعی و کوچک کنار تاریخ اصلی نمایش داده شود.
- REQ-037 — مبدأ فنی گاه‌شماری شاهنشاهی بر پایه سال ۵۵۹ پیش از میلاد/آغاز پادشاهی کوروش بزرگ باشد؛ جزئیات در CALENDAR-SPEC.
- REQ-038 — تبدیل سال هجری خورشیدی به شاهنشاهی طبق قاعده ثبت‌شده در CALENDAR-SPEC انجام شود.
- REQ-039 — Calendar Engine باید مرز نوروز را در تبدیل میلادی و edge caseهای سال لحاظ کند.
- REQ-040 — تاریخ اصلی منبع تاریخی و معادل شاهنشاهی باید همزمان قابل نگهداری باشند.
- REQ-041 — منطق تقویم نباید داخل UI تکرار یا پیاده‌سازی شود.
- REQ-042 — Calendar Engine باید طول ماه‌ها، کبیسه، روز هفته، محاسبات تاریخ و تبدیل‌ها را پوشش دهد.

## نیازمندی‌های MVP

- REQ-043 — MVP باید Calendar Engine و تقویم شاهنشاهی را شامل شود.
- REQ-044 — MVP باید Today، Historical/Important Events، Timeline و Person را شامل شود.
- REQ-045 — MVP باید Personal Events، Personal Person و Memories را شامل شود.
- REQ-046 — Search باید از معماری MVP حذف نشود و برای استفاده اصلی قابل مصرف باشد.
- REQ-047 — فارسی/انگلیسی و RTL/LTR باید از پایه معماری MVP پشتیبانی شوند.
- REQ-048 — PWA baseline باید در مسیر MVP پیاده‌سازی و اعتبارسنجی شود.

## نیازمندی‌های معماری و کیفیت

- REQ-049 — هر Entity و use case مهم باید قرارداد داده مشخص داشته باشد.
- REQ-050 — داده عمومی تاریخی و داده خصوصی کاربر باید از نظر مدل و دسترسی جدا باشند.
- REQ-051 — سیستم باید برای validation، testing و edge-case regression طراحی شود.
- REQ-052 — وضعیت loading/error/empty باید در application و frontend تعریف شود.
- REQ-053 — frontend باید روی application/domain logic سوار شود و منطق تاریخی در component پخش نشود.
- REQ-054 — هر مرحله توسعه باید در ROADMAP، STATUS و CHANGELOG قابل ردیابی باشد.

## نیازمندی‌های حساب کاربری و هویت

- REQ-055 — MVP باید ثبت‌نام و ورود ساده با نام کاربری و رمز عبور داشته باشد.
- REQ-056 — نام کاربری باید یکتا باشد و از یک سیاست «cross-platform-safe» شبیه قواعد رایج شبکه‌های اجتماعی پیروی کند: بدون فاصله و ایموجی، با مجموعه محدود و امنی از حروف لاتین، اعداد، نقطه و underscore؛ جزئیات دقیق regex در Architecture نهایی می‌شود.
- REQ-057 — نام کاربری برای uniqueness به‌صورت case-insensitive مدیریت شود تا دو حساب با تفاوت صرفاً در بزرگ/کوچک بودن حروف ایجاد نشوند.
- REQ-058 — رمز عبور نباید به‌صورت plaintext ذخیره شود و جزئیات hash/session در Architecture تعیین شود.
- REQ-059 — سیستم حساب کاربری در MVP فاقد قابلیت‌های اجتماعی، پروفایل عمومی و دنبال‌کردن باشد.

## نیازمندی‌های اشتراک‌گذاری

- REQ-060 — کاربر باید بتواند یک روز مشخص را به‌صورت یک Share Card مستقل با رویدادهای همان روز آماده اشتراک‌گذاری کند.
- REQ-061 — Share Card باید طراحی بصری مستقل، خاص و mobile/share-friendly داشته باشد و نباید صرفاً screenshot صفحه تقویم باشد.
- REQ-062 — Share Card یک قابلیت utility برای اشتراک‌گذاری است و به‌معنای فعال‌شدن social features نیست.

## مرزهای صریح MVP و محصول

- REQ-063 — Reminder/Notification در MVP خارج از Scope است.
- REQ-064 — کاربر در MVP امکان ایجاد یا پیشنهاد Event عمومی/تاریخی ندارد.
- REQ-065 — پنل Admin/CMS در MVP وجود ندارد.
- REQ-066 — نقشه و Location features در MVP وجود ندارند؛ داده مکانی در صورت نیاز آینده optional است.
- REQ-067 — Export/Import داده شخصی در MVP وجود ندارد.
- REQ-068 — اتصال به تقویم یا سرویس‌های تقویم سیستم‌عامل و سرویس‌های ثالث در MVP وجود ندارد.
- REQ-069 — مدل درآمدی، Subscription، تبلیغات و پرداخت در Scope محصول نیستند.
- REQ-070 — Public API در MVP وجود ندارد.
- REQ-071 — قابلیت‌های اجتماعی مانند پروفایل عمومی، follow، like، comment و social feed در MVP وجود ندارند.
- REQ-072 — معماری می‌تواند برای قابلیت‌های Deferred آماده باشد، اما این قابلیت‌ها تا زمان تصمیم مستقل فعال یا در UI نمایان نمی‌شوند.
