# REQUIREMENTS — نیازمندی‌های محصول

Version: 1.1.0
Status: APPROVED
Last updated: 2026-10-03

## نیازمندی‌های تأییدشده

- REQ-001 — محصول Mobile-first و App-like.
- REQ-002 — تقویم اصلی خورشیدی/ایرانی با نظام نمایش شاهنشاهی.
- REQ-003 — سال در UI با شماره شاهنشاهی نمایش داده شود؛ نمونه ۲۵۸۵.
- REQ-004 — نام ماه‌ها دقیقاً مطابق CALENDAR-SPEC، از جمله «اَمرداد» و «اسپند».
- REQ-005 — Today مرکز تجربه محصول باشد.
- REQ-006 — تقویم ماهانه با تعامل لمسی، navigation و جزئیات روز.
- REQ-007 — Event Entity ساختاریافته و قابل ارتباط.
- REQ-008 — داده تاریخی مهم باید منبع و وضعیت اعتبارسنجی داشته باشد.
- REQ-009 — مناسبت‌ها و داده تاریخی باید امکان بررسی و تأیید ماه‌به‌ماه داشته باشند.
- REQ-010 — صفحه مستقل Important Events.
- REQ-011 — Important Events باید ارائه بصری، تصویر باکیفیت و محتوای ساختاریافته داشته باشد؛ تصویر شاخص هر رویداد باید برای صفحه مستقل انتخاب/تهیه شود.
- REQ-012 — هر Event مهم باید صفحه جزئیات با روایت، تصاویر، افراد، دوره و منابع داشته باشد؛ مکان و نقشه در MVP الزامی نیستند.
- REQ-013 — Timeline مستقل تاریخ ایران.
- REQ-014 — Person Entity مستقل.
- REQ-015 — Personal Events شامل تولد، سالگرد و رویداد سفارشی است؛ قابلیت Reminder/Notification در MVP وجود ندارد.
- REQ-016 — Personal Person Entity.
- REQ-017 — Memories برای ثبت و یادآوری خاطرات.
- REQ-018 — Search برای Entityها و داده‌های شخصی قابل توسعه باشد.
- REQ-019 — رابط بر اساس صبح، ظهر، غروب و شب به‌صورت ظریف تغییر کند.
- REQ-020 — رابط بر اساس فصل به‌صورت ظریف تغییر کند.
- REQ-021 — فارسی و انگلیسی پشتیبانی شوند.
- REQ-022 — RTL/LTR واقعی و direction-aware.
- REQ-023 — PWA از نسخه اول به‌عنوان بخشی از هدف MVP در نظر گرفته شود.
- REQ-024 — Calendar Engine، Data/Domain، Application Logic، UI و Localization از هم جدا باشند.
- REQ-025 — محتوای تاریخی در UI hard-code نشود.
- REQ-026 — محتوای تاریخی و معاصر تا حد امکان source-backed و قابل بررسی باشد.
- REQ-027 — Swipe، Bottom Sheet، Touch Target و Motion هدفمند استفاده شوند.
- REQ-028 — محصول نباید به یک تقویم وب‌سایتی یا جدول مدرن تقلیل یابد.
- REQ-029 — Event، Person، Timeline، Memory و داده‌های مرتبط رابطه منطقی داشته باشند.
- REQ-030 — GitHub باید مرجع قابل ادامه پروژه باشد.
- REQ-031 — مخاطبان اصلی شامل ایرانیان، پادشاهی‌خواهان، ملی‌گرایان، علاقه‌مندان به شیر و خورشید، طرفداران شاهزاده رضا پهلوی و طرفداران پادشاهی و خاندان پهلوی باشند.
- REQ-032 — محصول برای افراد غیرایرانی نیز باید امکان آشنایی با فرهنگ و تاریخ ایران را فراهم کند.
- REQ-033 — کاربرد اصلی باید مانند یک تقویم آشنا و آزاد باشد و کاربر را به الگوی زمانی خاص محدود نکند.
- REQ-034 — پیچیدگی غیرضروری ممنوع؛ تفاوت محصول از هویت تقویم، محتوا و کیفیت تجربه بیاید.

- REQ-035 — سال هجری شمسی معمولی نباید در UI کاربر نمایش داده شود.
- REQ-036 — میلادی فقط به‌صورت فرعی و کوچک کنار تاریخ اصلی نمایش داده شود.
- REQ-037 — مبدأ فنی گاه‌شماری شاهنشاهی بر پایه سال ۵۵۹ پیش از میلاد/آغاز پادشاهی کوروش بزرگ باشد؛ جزئیات در CALENDAR-SPEC.
- REQ-038 — تبدیل سال هجری خورشیدی به شاهنشاهی طبق قاعده ثبت‌شده در CALENDAR-SPEC انجام شود.
- REQ-039 — Calendar Engine باید مرز نوروز را در تبدیل میلادی و edge caseهای سال لحاظ کند.
- REQ-040 — تاریخ اصلی منبع تاریخی و معادل شاهنشاهی باید همزمان قابل نگهداری باشند.
- REQ-041 — منطق تقویم نباید داخل UI تکرار یا پیاده‌سازی شود.
- REQ-042 — Calendar Engine باید طول ماه‌ها، کبیسه، روز هفته، محاسبات تاریخ و تبدیل‌ها را پوشش دهد.
- REQ-081 — Calendar Engine باید Today، Time-of-day و Seasonal state را به‌صورت domain/application contracts قابل تست ارائه کند.
- REQ-082 — CI پروژه باید حداقل typecheck، unit tests و production build را اجرا کند؛ تا مشاهده run موفق، PASS رسمی ثبت نشود.

- REQ-048 — PWA baseline باید در مسیر MVP پیاده‌سازی و اعتبارسنجی شود.

## نیازمندی‌های معماری و کیفیت

- REQ-049 — هر Entity و use case مهم باید قرارداد داده مشخص داشته باشد.
- REQ-050 — داده عمومی تاریخی و داده خصوصی کاربر باید از نظر مدل و دسترسی جدا باشند.
- REQ-051 — سیستم باید برای validation، testing و edge-case regression طراحی شود.
- REQ-052 — وضعیت loading/error/empty باید در application و frontend تعریف شود.
- REQ-053 — frontend باید روی application/domain logic سوار شود و منطق تاریخی در component پخش نشود.
- REQ-054 — هر مرحله توسعه باید در ROADMAP، STATUS و CHANGELOG قابل ردیابی باشد.


## معیارهای پذیرش MVP — Acceptance Criteria

این معیارها در سطح محصول تعریف شده‌اند و مرجع پذیرش برای تست، QA و Release هستند. هر معیار یک شناسه مستقل دارد. تا وقتی معیارهای الزامی Release با وضعیت PASS تأیید نشده باشند، MVP قابل پذیرش نهایی نیست.

### Calendar Engine

- AC-001 — تاریخ اصلی هر روز باید به‌صورت تاریخ شاهنشاهی خورشیدی قابل محاسبه و نمایش باشد.
- AC-002 — ترتیب و نام ماه‌ها باید دقیقاً مطابق CALENDAR-SPEC باشد، از جمله «اَمرداد» و «اسپند».
- AC-003 — شماره‌گذاری سال شاهنشاهی باید مطابق قاعده مصوب انجام شود و سال‌های قبل و بعد از سال فعلی نیز درست محاسبه شوند.
- AC-004 — طول ماه‌ها و قواعد کبیسه باید بدون خطای قابل مشاهده در محاسبات تقویم اعمال شوند.
- AC-005 — تبدیل شاهنشاهی/هجری خورشیدی و میلادی باید برای تاریخ‌های پشتیبانی‌شده با نتیجه صحیح انجام شود.
- AC-006 — مرز نوروز و تغییر سال باید در تبدیل و محاسبه تاریخ به‌درستی مدیریت شود.
- AC-007 — تاریخ تاریخی باید بتواند هم تاریخ اصلی منبع و هم معادل شاهنشاهی خود را بدون از دست رفتن اطلاعات نگه دارد.
- AC-008 — محاسبه روز هفته و عملیات پایه تاریخ (Date Arithmetic) باید درست و قابل تست باشند.
- AC-009 — منطق تقویم نباید در UI یا componentهای نمایشی پیاده‌سازی تکراری داشته باشد و باید از Calendar Engine مصرف شود.

### Today و Calendar Experience

- AC-010 — صفحه Today باید حداقل تاریخ شاهنشاهی، میلادی کوچک، روز هفته و بخش‌های مرتبط با مناسبت/رویداد و لایه شخصی را در صورت وجود داده نمایش دهد.
- AC-011 — Monthly Calendar باید ماه کامل را نمایش دهد و جابه‌جایی ماه قبل/بعد و بازگشت به Today را پشتیبانی کند.
- AC-012 — انتخاب یک روز باید Day Detail معتبر و سازگار با داده‌های همان روز ارائه کند.
- AC-013 — وجود رویداد یا داده شخصی در روزهای تقویم باید به‌صورت marker یا نشانه بصری قابل تشخیص باشد.
- AC-014 — تعاملات لمسی اصلی، از جمله swipe در calendar، باید روی touch device قابل استفاده و بدون رفتار غیرمنتظره باشند.

### Historical / Event / Timeline

- AC-015 — Event، Person و Timeline باید از داده ساختاریافته تغذیه شوند و اطلاعات اصلی در UI hard-code نشود.
- AC-016 — داده تاریخی مهم باید source metadata و وضعیت validation داشته باشد و اطلاعات فاقد وضعیت مشخص وارد محتوای نهایی نشود.
- AC-017 — Important Events باید صفحه مستقل داشته باشد و هر رویداد منتخب تصویر شاخص مناسب برای نمایش داشته باشد.
- AC-018 — Event Detail باید بتواند تاریخ، روایت، تصاویر، افراد مرتبط، دوره و منابع موجود را به‌صورت ساختاریافته نمایش دهد.
- AC-019 — Historical Timeline باید امکان مرور حداقل نسخه اولیه دوره‌ها/رویدادهای تعریف‌شده و اتصال آنها به محتوای مرتبط را فراهم کند.
- AC-020 — Person page باید مستقل باشد و بتواند به Eventها و سایر Entityهای مرتبط لینک شود.

### Personal Layer

- AC-021 — محتوای عمومی باید بدون ورود قابل مشاهده باشد و دسترسی به داده‌های شخصی به حساب همان کاربر محدود شود.
- AC-022 — کاربر واردشده باید بتواند Personal Event را مطابق مدل محصول ایجاد، مشاهده و ویرایش کند.
- AC-023 — Recurrence پایه باید برای Personal Eventهای پشتیبانی‌شده نتیجه قابل پیش‌بینی و قابل تست داشته باشد.
- AC-024 — کاربر واردشده باید بتواند Memory را به تاریخ مناسب متصل، مشاهده و ویرایش کند.
- AC-025 — داده عمومی و داده خصوصی باید در مدل و مسیر دسترسی از یکدیگر تفکیک شوند و داده شخصی کاربر نباید در query عمومی نشت کند.
- AC-026 — Share Card فقط برای Personal Event تولید شود، به‌صورت تصویر مستقل باشد، تاریخ شاهنشاهی و میلادی کوچک و جزئیات رویداد را داشته باشد، تم مناسب نوع رویداد را اعمال کند و از Share Sheet قابل اشتراک‌گذاری باشد.

### Search و Localization

- AC-027 — Search باید بتواند در محدوده MVP، Event، Person، Timeline/Period، مناسبت، ماه، Personal Event و Memory را جستجو و نتایج را به Entity مرتبط هدایت کند.
- AC-028 — رابط فارسی و انگلیسی باید از نظر محتوا، labels و stateهای اصلی قابل استفاده باشند.
- AC-029 — RTL برای فارسی و LTR برای انگلیسی باید به‌صورت واقعی و direction-aware اجرا شوند و layout صرفاً با تغییر متن شکسته نشود.
- AC-030 — state مربوط به زمان روز و فصل باید بر پایه داده/منطق مشخص و با تغییر ظریف در تجربه ارائه شود و مانع استفاده از محصول نشود.

### Authentication و PWA

- AC-031 — ثبت‌نام و ورود با Username/Password طبق REQUIREMENTS کار کند؛ uniqueness نام کاربری و حداقل طول رمز باید enforce شود.
- AC-032 — Session کاربر باید تا Logout یا انقضایی که بعداً در Architecture تعریف می‌شود، رفتار مورد انتظار را حفظ کند.
- AC-033 — PWA baseline شامل manifest و قابلیت نصب پایه باید در محیط‌های پشتیبانی‌شده قابل اعتبارسنجی باشد.
- AC-034 — ساختار تعامل محصول باید در موبایل app-like، touch-friendly و دارای loading/error/empty stateهای قابل استفاده باشد.

### کیفیت، تست و Scope

- AC-035 — تست‌های واحد مربوط به Calendar Engine، conversion و edge caseهای سال باید وجود داشته باشند و در CI قابل اجرا باشند؛ پذیرش نهایی منوط به PASS شدن CI است.
- AC-036 — مدل‌های اصلی Event، Person، Personal Event و Memory باید تست‌های رفتاری/قراردادی پایه داشته باشند.
- AC-037 — تغییرات مربوط به مرز سال، conversion، recurrence و داده‌های شخصی باید دارای regression coverage باشند تا تغییرات بعدی منطق قبلی را نشکنند.
- AC-038 — هیچ قابلیت خارج از Scope مصوب MVP نباید برای تکمیل یک acceptance criterion به‌صورت پنهان وارد محصول شود.
- AC-039 — معیار پذیرش نهایی MVP باید بر اساس نتیجه تست و QA بررسی شود، نه صرفاً ظاهر صفحه یا وجود کد.
- AC-040 — وضعیت test/build نباید بدون مشاهده نتیجه اجرا PASS اعلام شود.

## ادامه PHASE-01 پس از REQUIREMENTS v1.0

Requirements v1.0 در سطح محصول، Scope، MVP، Acceptance، Account/Auth و Share Card نهایی و APPROVED است.

موارد زیر دیگر «ناتمام بودن Requirements» محسوب نمی‌شوند؛ این‌ها specificationهای تفصیلی مدل محتوا و قراردادهای دامنه هستند و در TASKهای بعدی PHASE-01 به‌صورت مستقل تکمیل می‌شوند:
- TASK-01-009 — Event Model
- TASK-01-010 — Person Model
- TASK-01-011 — Memory Model
- TASK-01-012 — Personal Event Model
- TASK-01-013 — Important Event & Editorial Selection
- TASK-01-014 — Timeline & Entity Relationships
- TASK-01-015 — Sources, Verification & Editorial Policy
- TASK-01-016 — Media/Asset Content Model
- TASK-01-017 — Historical Date Representation
- TASK-01-018 — Search Requirements

Account/Auth و Personal Share Card در سطح Requirements نهایی هستند؛ جزئیات فنی آن‌ها در PHASE-02 به معماری منتقل می‌شوند.


## نیازمندی‌های حساب کاربری و هویت

- REQ-055 — MVP باید ثبت‌نام و ورود حداقلی با نام کاربری و رمز عبور داشته باشد؛ ورود برای استفاده از محتوای عمومی الزامی نیست.
- REQ-056 — نام کاربری باید یکتا باشد و از یک سیاست «cross-platform-safe» شبیه قواعد رایج شبکه‌های اجتماعی پیروی کند: بدون فاصله و ایموجی، با مجموعه محدود و امنی از حروف لاتین، اعداد، نقطه و underscore؛ جزئیات دقیق regex در Architecture نهایی می‌شود.
- REQ-057 — نام کاربری برای uniqueness به‌صورت case-insensitive مدیریت شود تا دو حساب با تفاوت صرفاً در بزرگ/کوچک بودن حروف ایجاد نشوند.
- REQ-058 — رمز عبور نباید به‌صورت plaintext ذخیره شود و جزئیات hash/session در Architecture تعیین شود.
- REQ-059 — سیستم حساب کاربری در MVP فاقد قابلیت‌های اجتماعی، پروفایل عمومی و دنبال‌کردن باشد.

## نیازمندی‌های اشتراک‌گذاری

- REQ-060 — Share Card در MVP فقط برای یک رویداد شخصیِ متعلق به کاربر ساخته می‌شود.
- REQ-061 — Share Card باید به‌صورت تصویر واقعی و مستقل تولید شود و نباید صرفاً screenshot صفحه محصول باشد.
- REQ-062 — اطلاعات Share Card شامل تاریخ شاهنشاهی، روز هفته، میلادیِ کوچک و جزئیات رویداد خصوصی همان کاربر است.
- REQ-063 — Share Card باید براساس نوع/انتخاب رویداد شخصی تم مناسب داشته باشد؛ برای نمونه رویداد تولد تم تولد و برای «سایر» یک طراحی ساده، شیک و متمایز داشته باشد.
- REQ-064 — کاربر باید بتواند Share Card را از طریق Share Sheet سیستم‌عامل/مرورگر برای اپ‌های ارتباطی موجود ارسال کند.
- REQ-065 — Share Card یک قابلیت utility خصوصی است و به‌معنای فعال‌شدن social system نیست.

## مرزهای صریح MVP و محصول

- REQ-066 — Reminder/Notification در MVP خارج از Scope است.
- REQ-067 — کاربر در MVP امکان ایجاد یا پیشنهاد Event عمومی/تاریخی ندارد.
- REQ-068 — پنل Admin/CMS در MVP وجود ندارد.
- REQ-069 — نقشه و Location features در MVP وجود ندارند؛ داده مکانی در صورت نیاز آینده optional است.
- REQ-070 — Export/Import داده شخصی در MVP وجود ندارد.
- REQ-071 — اتصال به تقویم یا سرویس‌های تقویم سیستم‌عامل و سرویس‌های ثالث در MVP وجود ندارد.
- REQ-072 — مدل درآمدی، Subscription، تبلیغات و پرداخت در Scope محصول نیستند.
- REQ-073 — Public API در MVP وجود ندارد.
- REQ-074 — قابلیت‌های اجتماعی مانند پروفایل عمومی، follow، like، comment و social feed در MVP وجود ندارند.
- REQ-075 — حذف حساب کاربری در MVP وجود ندارد.
- REQ-076 — فراموشی/بازیابی رمز عبور در MVP وجود ندارد.
- REQ-077 — ورود به محصول برای مشاهده محتوای عمومی الزامی نیست؛ حساب کاربری فقط برای امکانات شخصی لازم است.
- REQ-078 — Session کاربر تا Logout یا انقضای امنیتی تعریف‌شده در Architecture حفظ می‌شود.
- REQ-079 — ثبت‌نام و ورود باید حداقلی و بسیار ساده باشند.
- REQ-080 — معماری می‌تواند برای قابلیت‌های Deferred آماده باشد، اما این قابلیت‌ها تا زمان تصمیم مستقل فعال یا در UI نمایان نمی‌شوند.
