# Editorial Event Review Workflow

## هدف

رویدادهای تاریخی عمومی پروژه بدون بررسی و تأیید جداگانه وارد محصول نمی‌شوند.

## وضعیت فعلی

- `seedEvents` عمداً خالی است.
- صفحهٔ «رویدادهای خاص» و بخش رویدادهای روزانه از همین منبع استفاده می‌کنند و در نبود داده، حالت خالی مناسب نشان می‌دهند.
- هیچ رویداد تاریخی جدیدی نباید صرفاً برای پر کردن UI به seed اضافه شود.

## روند ماه‌به‌ماه

برای هر ماه تقویم شاهنشاهی، پیش از انتشار:

1. فهرست نامزدهای رویدادهای آن ماه تهیه می‌شود.
2. برای هر نامزد، تاریخ، عنوان، خلاصه، نوع رویداد و منابع بررسی می‌شود.
3. موارد قابل‌مناقشه یا دارای تاریخ/منبع نامطمئن جداگانه علامت‌گذاری می‌شوند.
4. فهرست نهایی برای بررسی و تأیید کاربر ارائه می‌شود.
5. فقط مواردی که کاربر تأیید کرده است وارد `seedEvents` می‌شوند.
6. پس از ورود داده، تست‌های محتوایی و relationship validation اجرا می‌شوند.

## قانون تأیید

«پیشنهاد شده» با «تأیید شده برای انتشار» یکی نیست.

تا زمانی که تأیید صریح انجام نشده است:
- رویداد وارد seed نمی‌شود.
- `featured` برای آن فعال نمی‌شود.
- در صفحهٔ روز، صفحهٔ رویدادهای خاص، جست‌وجوی عمومی یا Timeline به‌عنوان رویداد منتشرشده نمایش داده نمی‌شود.

## ترتیب بررسی

ماه‌ها به‌ترتیب بررسی می‌شوند و بعد از پایان هر ماه، نتیجه و موارد تأییدشده ثبت می‌شود. سپس به ماه بعد می‌رویم.


## قرارداد تجربه Important Events و Event Detail

این قرارداد قبلاً در REQUIREMENTS و IMPORTANT-EVENTS-MODEL تصویب شده و بخشی از scope اصلی است؛ نباید به‌عنوان نیازمندی جدید تلقی شود.

صفحهٔ Important Events باید رویدادهای مهم همان ماه را با تصویر شاخص نمایش دهد. هر card باید قابل کلیک باشد و به Event Detail مستقل برود. Detail باید توضیح/روایت کامل‌تر، تاریخ، افراد/دوره‌های مرتبط، منابع و در صورت وجود تصاویر یا اسناد بیشتر را نمایش دهد.

در وضعیت فعلی:
- ساختار listing و لینک‌دهی Detail موجود است.
- seed رویدادهای تاریخی عمداً خالی است.
- پیاده‌سازی نمایش hero/gallery هنوز ناقص است و باید همراه با کار Media/Content تکمیل شود.
